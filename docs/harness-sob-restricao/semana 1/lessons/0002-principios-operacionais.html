Princípios que sobrevivem ao prompt

Ao terminar, você poderá auditar um workflow agentic usando cinco perguntas: onde vive o estado, qual é o contrato, quem valida, quais são os limites e que evidência permanece.

estadocontratosgatesevidência

Uma lente, não uma lista de features

IAO não é definido por usar JSON, Git ou uma linguagem específica. Esses são mecanismos da implementação. O padrão se mantém quando cinco propriedades estruturais continuam verdadeiras:

1 · Estado fora do chat

O run se reconstitui de arquivos autoritativos, não da memória conversacional.

2 · Contrato por turno

Cada instrução diz o input e a forma de resposta esperada.

3 · Gate antes do avanço

O harness observa realidade verificável antes de aceitar a transição.

4 · Loop limitado

Passos, tempo, retries, tamanho e efeitos têm limites explícitos.

5 · Evidência persistente

A trajetória pode ser examinada sem depender do histórico do chat.

6 · Política separada

O engine fornece mecanismo; o flow concentra regras do domínio.

1. Estado fora da conversa

Cada invocação do harness é um processo novo. Continuidade vem de state.json, run_config.json, backlog, trace, progress.txt e Git.1 Isso permite resetar o contexto entre features e até trocar o driver sem depender de uma recapitulação perfeita.

Uma boa pergunta de projeto: “Se o chat desaparecesse agora, quais arquivos permitiriam continuar sem adivinhar?”

2. Um contrato estreito por turno

O envelope reduz a conversa a um comando estruturado. O harness emite <input> e <response>; o driver realiza somente a etapa ativa e devolve a forma solicitada. Comandos malformados recebem erro corretivo em vez de um término silencioso.2

Contrato estreito não é só estética. Ele impede que o modelo precise carregar o estado inteiro e torna parsing, validação e testes independentes do provedor.

3. Realidade antes de autodeclaração

O agent pode propor; o ambiente deve confirmar. No Development, o resumo vem do diff, a verificação vem do exit code e o handoff inspeciona o repositório. Texto PASS ou um hash enviado pelo driver não fecha a feature.3

AlegaçãoEvidência melhor
“Implementei a feature.”Diff limitado + gate executável.
“Os testes passaram.”Exit code, log e ambiente identificável.
“O handoff foi feito.”Commit e working tree inspecionados.
“Terminamos.”Backlog sem itens pendentes e estado terminal tipado.

4. O loop também é produto

Loop engineering chama atenção para a estrutura da iteração: feedback, checkpoints, condições de saída e limites. No código atual, o Development limita features, passos por feature e revisões do plano; o engine aplica budgets e timeout.4 Um loop sem saída definida transforma autonomia em custo acumulado.

5. Evidência é parte do resultado

Trace registra cada comando externo, outcome, custo em bytes, timestamp e o hash da linha anterior. HarnessLog registra entrada e saída de tasks; snapshots congelam o estado ao encerrar.5 O objetivo não é registrar o raciocínio privado do modelo, mas sustentar afirmações operacionais sobre o run.

6. Mecanismo e domínio não se misturam

Harness.Engine não sabe o que é uma feature. Ele sabe parsear, limitar, despachar, persistir e emitir. Flows.Development sabe planejar, selecionar, verificar e fazer handoff. Essa separação é o que permite testar o workflow como código e trocar drivers sem reescrever a política.

O princípio que impede uma conclusão perigosa

Controle determinístico não implica execução segura. Se o workspace pode alterar política, verificador e evidência, um harness pode repetir com grande consistência uma ação insegura. O RFC trata agent e target como não confiáveis e propõe policy protegida, capability broker, approvals e verificação independente para os níveis Controlled/Assured.6

A baseline atual oferece propriedades valiosas de IAO Core, mas não deve ser apresentada como fronteira de segurança completa. Em particular, o verify-feature.sh preferido vive no target editável pelo agent, e o auto-handoff cria commit automaticamente. Para um piloto local e reversível isso pode ser aceitável; para código sensível, é uma decisão explícita de risco.

Prática: audite um workflow em cinco perguntas

Pense em um uso seu — por exemplo, “corrigir issues automaticamente”. Sem desenhar a solução ainda, escreva uma linha para cada pergunta:

  1. Estado: o que precisa sobreviver ao chat?
  2. Contrato: qual resposta mínima cada etapa devolve?
  3. Gate: o que o ambiente pode provar antes de avançar?
  4. Limite: quando o sistema deve parar mesmo sem sucesso?
  5. Evidência: o que alguém verificará amanhã?
