Do driver ao projeto-alvo

Ao terminar, você conseguirá seguir um turno pelas cinco camadas, localizar a autoridade de cada componente e descrever o loop Development implementado hoje.

drivertransportengineflowtarget

A pilha inteira em uma frase

O driver entrega uma resposta pelo transport; o engine aplica protocolo e guardrails; o flow executa a política do domínio; o target fornece os efeitos e a realidade que os gates observam.

A · Driver

IDE agent. Lê a instrução, usa ferramentas, altera o target e devolve JSON. Não escolhe a transição.

B · Transport

inbox.json entra; stdout sai. stderr fica reservado a diagnóstico.

C · Engine

Host, registry, parser, guards, prompt, config, stores, trace e infraestrutura.

D · Flow

Política específica: tasks, transições, feature DAG, verificação, handoff e replan.

E · Target

Código, testes, init.sh, verificador, progresso e Git — editável, portanto não confiável por padrão.

Siga um turno

O fluxo real não é uma conversa contínua dentro de um processo. Cada chamada ao runner cria uma nova invocação; a continuidade é reconstruída de stores.

entrada
Inbox ou argv

O adapter prefere escrever JSON real em .harness/inbox.json para evitar escaping frágil.

host
HarnessHost

É a entrada reutilizável e o único componente que escreve a resposta de controle em stdout.

dispatch
TaskRegistry

Parseia, decide reset/resume, aplica latch, budget, timeout e roteia pelo comando.

política
Task do flow

Lê e altera stores, observa o target e devolve o próximo prompt ou stop.

saída
Trace + instrução

O outcome é persistido; PromptFormatter apresenta input, response e a skill da etapa.

O próximo “estado” não é um enum completo persistido. Na implementação, ele é materializado pelo comando do envelope que a task devolve; HarnessState guarda passo, dados, contexto, custo e motivo terminal.1 É uma máquina de estados por protocolo e transições, não necessariamente por uma classe chamada StateMachine.

Engine fornece mecanismo; flow fornece significado

O loop Development observado no código

Num run novo, start lê specs/ e pede um plano. O planner grava .harness/plan.json; plan valida o DAG, limita a dez features e persiste targetDir, verificador e runId. Depois o próprio harness faz bearings, smoke e pick antes de emitir o turno criativo de implementação.2

start
  ├─ novo → plan ───────────────────────┐
  └─ resume ────────────────────────────┤
                                       ▼
            [bearings → smoke → pick] internos
                                       ↓
                                  implement
                                       ↓
                                  auto-verify
                     ┌── FAIL ──────────┴──── PASS ─┐
                     │                              │
                     └─ fix → implement      auto-handoff
                          └─ 3ª falha               ↓
                               → replan       próxima feature
                                                  ou stop

Se a verificação falhar três vezes e ainda houver quota, o harness registra uma observação e pede uma proposta de replan. Um avaliador determinístico verifica alternativas, cobertura, preservação do que já passou, DAG e budget; só então a revisão é aplicada. O limite atual é duas revisões.3

Documentação versus implementação: README e ARCHITECTURE ainda descrevem uma máquina de oito comandos. Program.cs registra nove: start, plan, replan, bearings, smoke, pick, implement, verify e handoff.4 Aprender a comparar diagrama, composição e código faz parte da leitura arquitetural.

Onde termina o harness?

O engine deliberadamente não inclui um cliente de API de modelo e não fornece sandbox. O driver é a conexão ao modelo e o ambiente/IDE fornece permissões.5 Essa fronteira mantém o core portátil, mas cria a tensão central com o RFC Controlled, que exige mediação de efeitos por um control plane protegido.

Outro detalhe: o target também guarda parte da memória operacional — init.sh, verify-feature.sh, progress.txt e Git. Isso permite sessões limpas, porém o mesmo agent pode editar alguns desses artefatos. Persistência resolve continuidade; não resolve sozinha integridade ou independência.
