Parte A · seja o driver por três turnos

O flow HelloWorld elimina planejamento, Git e edição. Você fará manualmente o papel do agent: envia start, lê a instrução, responde ping, responde pong e observa stop.1

Pré-requisito: .NET SDK compatível com net10.0. O wrapper compila o flow no primeiro uso. O laboratório grava apenas num diretório temporário.

1. Crie o laboratório e guarde o caminho do repositório

cd /Users/yanjustino/Documents/cooperacode.club/IAO
IAO_REPO="$(pwd)"
IAO_LAB_DIR="$(mktemp -d)"
cd "$IAO_LAB_DIR"
printf 'Laboratório: %s\n' "$IAO_LAB_DIR"

2. Envie os três envelopes

"$IAO_REPO/src/dotnet/run-helloworld.sh" \
  '{"type":"text","value":"start"}'

"$IAO_REPO/src/dotnet/run-helloworld.sh" \
  '{"type":"text","value":"ping","args":["ping"]}'

"$IAO_REPO/src/dotnet/run-helloworld.sh" \
  '{"type":"text","value":"pong","args":["pong"]}'

As saídas esperadas são: uma instrução pedindo ping, uma instrução pedindo pong e, por fim, exatamente stop. Os args aparecem porque os validators atuais verificam também o primeiro argumento; o exemplo argv no README omite esse detalhe, embora o contrato emitido pelo próprio flow o inclua.2

3. Leia a memória que ficou

find .harness -maxdepth 1 -type f -print | sort
sed -n '1,20p' .harness/last-helloworld.trace.jsonl
sed -n '1,80p' .harness/last-helloworld.state.json

Procure três fatos: passos monotônicos, comandos na ordem start → ping → pong e outcome final stop. Depois abra trace.jsonl e observe que cada linha, exceto a gênese, referencia o hash da anterior.

O ganho desta parte não é “rodar três comandos”. É perceber que o run pode ser reconstruído de estado e trace mesmo que a conversa que o conduziu desapareça.

Parte B · prepare um piloto Development

Não execute esta parte diretamente numa branch com trabalho em andamento. O flow faz stage e commit automáticos; seu primeiro piloto deve ter raio de impacto pequeno.

1. Escolha engine e driver

A trilha recomendada para começar é engine Python + driver Codex. Ela exige Python 3.11+ no target, Bash e Git; a linguagem do projeto-alvo pode ser outra. Se seu objetivo for estudar ou estender o core canônico, escolha .NET depois.

2. Empacote a baseline

cd /Users/yanjustino/Documents/cooperacode.club/IAO
./package.sh --engine python --ide codex

Na baseline 0.5.0, o resultado é dist/flows-python-v0.5.0/. Reexecutar o mesmo empacotamento remove e recria esse diretório exato; não mantenha trabalho manual dentro dele.3

3. Inspecione antes de copiar

find dist/flows-python-v0.5.0 -maxdepth 3 -type f -print | sort
sed -n '1,220p' dist/flows-python-v0.5.0/.harness/START-HERE.md
sed -n '1,160p' dist/flows-python-v0.5.0/.codex/agents/development.toml
sed -n '1,120p' dist/flows-python-v0.5.0/harness.json

O pacote instala engine, skills, scripts, wrapper, config e adapter. Revise conflitos com arquivos que seu projeto já possui. O harness.json referencia harness.schema.json, mas o empacotador atual não copia o schema; leve-o separadamente se quiser validação/autocomplete no editor.

4. Prepare o target

  • Use um clone descartável ou crie uma branch dedicada.
  • Exija git status --short vazio antes da cópia.
  • Garanta que Git tenha identidade de commit configurada.
  • Confirme um comando real de verificação, como dotnet test, npm test, pytest ou go test ./....
  • Não deixe segredos ou mudanças não relacionadas no working tree.

Copie um pacote explícito, sem glob ambíguo:

IAO_TARGET="/caminho/absoluto/do/projeto-piloto"
cp -R dist/flows-python-v0.5.0/. "$IAO_TARGET/"
cp harness.schema.json "$IAO_TARGET/harness.schema.json"

5. Escreva um brief pequeno

Crie specs/primeiro-piloto.md com esta estrutura:

# Objetivo
Adicionar uma capacidade pequena e observável.

## Escopo
- No máximo 2–3 comportamentos.

## Fora de escopo
- Deploy, migração destrutiva, credenciais e integrações externas.

## Restrições
- Preservar a arquitetura existente.
- Alterar somente <pastas permitidas>.

## Aceitação
- <comando de build/lint/test> passa.
- Cada comportamento possui teste reproduzível.

O planner lê o brief uma vez e distribui contexto limitado para cada feature. Critérios vagos produzem gates vagos; o harness não transforma “parece bom” em prova.

6. Reduza a configuração ao necessário

O Quickstart e o arquivo empacotado divergem. Para um piloto curto, revise conscientemente cada valor; um ponto de partida conservador é:

{
  "$schema": "./harness.schema.json",
  "maxSteps": 12,
  "maxInstructionChars": 0,
  "docsMaxChars": 40000,
  "docsFolder": "specs",
  "timeoutMs": 60000,
  "contextResetMode": "per-feature",
  "contextResetThreshold": 0.7,
  "contextFallbackFeatures": 1
}

maxSteps é substituído pelo budget maior do Development. O timeout deve acomodar o seu gate real, mas não use os dez minutos do teto atual sem necessidade. A configuração do workspace melhora previsibilidade; ela ainda não é uma policy protegida no sentido do RFC.

7. Inicie pelo adapter, não pelo shell

Abra a raiz do target no Codex e peça:

Use o agente customizado development para desenvolver: <objetivo curto do brief>.

O adapter escreve start na inbox, executa o wrapper, cumpre o contrato e continua até stop. Quando aparece === NEW SESSION (clean context) ===, ele delega a feature a um subagente novo; o adapter principal permanece responsável pelo transport.4

8. Observe antes de confiar

Durante e depois do run, inspecione:

  • .harness/feature_list.json — backlog e dependências;
  • .harness/trace.jsonl e snapshots — trajetória;
  • .harness/logs/ — saída dos gates;
  • progress.txt — handoff humano;
  • git log e git status — efeitos reais.
Limite do piloto: o auto-handoff executa git add -A no target, excluindo apenas .harness. O verificador preferido também pode viver no target editável. Mantenha o run local e reversível; não conceda push, deploy ou segredos até projetar controles independentes.

Dois detalhes que evitam falhas silenciosas

  1. Verificação não é um programa shell. O harness tokeniza um vetor de argumentos e rejeita operadores como pipe, redirecionamento, ;, &, $ e backticks. Para uma sequência complexa, implemente um verify-feature.sh explícito.
  2. verifyCmds roda em paralelo. Use somente gates independentes que não escrevam no mesmo arquivo. O planner atual não preenche esse array automaticamente.

Recuperação ativa · evidência do piloto

O que sustenta o run amanhã?

As alternativas têm exatamente as mesmas palavras.

Escolha pensando no que sobrevive ao contexto.
Leitura primária recomendada: faça a Parte A lado a lado com o README do HelloWorld. Antes da Parte B, leia o Quickstart e confronte cada comando com o pacote efetivamente gerado.

Para transformar execução em aprendizagem: envie ao agente professor as três linhas do trace HelloWorld e explique, com suas palavras, quem decidiu cada transição. Essa resposta é evidência suficiente para criar o primeiro learning record.
