Da ideia ao código, sem pular a autorização

Ao terminar, você terá uma arquitetura concreta para gerar PRDs e especificações rastreáveis, aprová-las e entregá-las ao flow Development sem transformar um parecer do modelo em permissão para editar código.

Flows.SpecificationPRD + SRS + SDDdigestshandoff.NET

A decisão arquitetural

Seu sistema deve ter dois flows completos. O novo Flows.Specification governa a transformação documental inteira; o Flows.Development existente governa plano, código, verificação e Git. PRD, SRS e SDD são fases causalmente ligadas de um mesmo run — não três flows independentes.

Um run documental

Quando o PRD muda, requisitos e design posteriores podem ficar obsoletos. Um único run ID, uma cadeia de digests e uma recascata controlada preservam essa relação.

Uma autorização entre flows

Gerar um bundle não concede automaticamente autoridade para alterar código. O início do Development continua uma ação explícita e separada.

Você não começa do zero

Uma branch histórica do repositório já implementou Flows.Refinement em .NET. Ela conduzia discover → planning → analysis → design → review, publicava Project Charter, SRS, SDD e Readiness Handoff e permitia recascata até duas vezes.1 O main atual não contém esse flow, mas preserva um bundle TodoApp produzido por ele.2

Estratégia: trate a branch histórica como código-fonte de projeto. Porte as ideias e os testes contra o engine atual; não faça merge cego. O novo nome Flows.Specification deixa explícito o produto desta evolução.

O LLM produz significado dentro das fases. Código .NET valida predicados, persiste artefatos, escolhe a próxima instrução, invalida derivados e aplica limites. O humano resolve conflitos materiais e autoriza o digest exato que será publicado.

JSON é a fonte; Markdown é a projeção

O flow histórico recebia documentos completos nos argumentos do envelope. Para o seu projeto, artefatos grandes devem viajar por arquivos de proposta. Depois da validação, o flow normaliza o JSON, calcula SHA-256 e só então renderiza Markdown de forma determinística.

{
  "schema": "iao/prd/v1",
  "ideaDigest": "sha256:…",
  "vision": "…",
  "goals": [
    { "id": "OBJ-001", "outcome": "…" }
  ],
  "successMetrics": [
    { "id": "MET-001", "measure": "…", "target": "…" }
  ],
  "nonGoals": ["…"],
  "scope": ["…"],
  "risks": [
    { "id": "RSK-001", "impact": "…", "mitigation": "…" }
  ],
  "blockingQuestions": []
}

A cadeia ideaDigest → prdDigest → srsDigest → sddDigest → bundleDigest impede que uma aprovação antiga seja reutilizada depois de uma revisão. Ela prova qual versão foi aprovada; em perfil Core, ainda não prova a identidade de quem aprovou.

Fronteira de confiança: se o mesmo agent consegue escrever approval.json, esse arquivo é um gate de processo, não uma aprovação autoritativa. Para uso Controlled, a decisão precisa vir de uma autoridade externa ao workspace gravável pelo agent.

O contrato real com Development

Hoje, Development não entende “PRD”. Ele lê todos os arquivos .md e .txt no nível raiz de docsFolder, ordena pelo nome, concatena e corta o conjunto ao atingir docsMaxChars em bytes UTF-8.3 Não valida status, aprovação, conflitos nem rastreabilidade.

Use um diretório ativo dedicado e nomes que expressem a ordem:

specs/active/
  00-prd.md
  10-software-requirements-specification.md
  20-software-design-document.md
  30-readiness-handoff.md

Antes de promover, o DevelopmentReadinessEvaluator deve provar que:

  • os quatro arquivos vieram do mesmo run e correspondem ao manifesto;
  • o bundle aprovado ainda possui o mesmo digest;
  • o campo de pendências bloqueadoras está vazio e não há fatia com referência quebrada;
  • as dependências das fatias formam um DAG e existe pelo menos uma fatia inicial;
  • a soma que Development realmente lerá fica abaixo do docsMaxChars configurado;
  • a publicação não sobrescreve arquivo que não pertença ao manifesto anterior.

O planner downstream transforma o bundle neste shape e depois entrega a cada sessão somente o contexto limitado da feature:4

[
  {
    "id": 1,
    "title": "…",
    "priority": 1,
    "dependsOn": [],
    "description": "…",
    "references": ["OBJ-001", "RF-001", "AC-001"],
    "implementationContext": {
      "requirements": ["…"],
      "constraints": ["…"],
      "files": ["…"],
      "acceptance": ["…"]
    }
  }
]
Dois limites downstream: Development retém no máximo dez features e não volta a injetar o brief inteiro durante a implementação. Portanto, cada fatia precisa carregar referências e aceitação suficientes; iniciativas maiores devem ser divididas em runs, não truncadas silenciosamente.

Mantenha Program.cs como composition root: registra comandos, validators, budget, política de resume e snapshots. Coloque transições em SpecificationTasks; regras puras em evaluators; persistência e digests no store; renderização e promoção em componentes próprios. Use source-generated JSON serialization para preservar compatibilidade com Native AOT.

Ordem de implementação

  1. Contrato: modelos JSON, renderer e golden files para o bundle TodoApp.
  2. Gates: evaluators puros para IDs, referências, cobertura, DAG, bytes e digests.
  3. Flow: happy path, retry corretivo, recascata, budget, timeout e resume.
  4. Aprovação/publicação: preview, digest, collision safety, staging e manifest-last.
  5. Integração: provar que DocsReader lê exatamente o bundle e que o planner preserva referências/aceitação.
Melhoria de fase 2: um development-seed.json poderia eliminar o segundo fatiamento pelo planner. O Development atual ignora JSON, então isso exige um contrato novo de importação; não faça o Specification escrever diretamente em .harness/plan.json.

Prática: construa uma linha de rastreabilidade

Escolha uma ideia pequena e escreva quatro linhas: um OBJ-001, um RF-001 que o satisfaz, um AC-001 binário e uma fatia que os referencia. Depois classifique cada verificação como LLM, código ou humano. Se você enviar essa resposta ao agente professor, ela se torna evidência real para a próxima lição.
